## The 4-way feature stack-up: none / adaptive / bloom / both

The most important plots in this directory are 10–16. They run the
exact same SIFT1M index four ways, varying only **(probe count, gate
active)**:

| condition | probe count | gate | what it is |
|---|---|---|---|
| **none**     | `probe_base` | off | no adaptive nprobe, no bloom — predicate-blind SPANN |
| **adaptive** | `filter_aware_nprobe(probe_base, sel)` | off | the existing adaptive-nprobe feature alone |
| **bloom**    | `probe_base` | on  | the new bloom gate alone |
| **both**     | `filter_aware_nprobe(probe_base, sel)` | on  | production target — both features composed |

`filter_aware_nprobe` is the production formula already on `main`:
`clip(base / max(sel, 0.001), base, base · 8)`. At ≤ 12.5 % selectivity
the boost saturates at 8×.

### Headline: the Pareto plot ([`12_4way_pareto_sel1pct.png`](12_4way_pareto_sel1pct.png))

Recall@10 plotted against the actual PL fetches per query. Each line is
one strategy swept across `probe_base ∈ {8, 16, 32, 64, 128}`.

- **Gray (`none`)**: the dominated curve — every other strategy reaches
  the same recall at fewer PL fetches.
- **Green (`adaptive`)**: hits high recall but at high I/O. To reach
  recall ≥ 0.95 you read ~256 PLs.
- **Blue (`bloom`)**: shifted left from gray — the gate cuts wasted
  fetches. But probe budget is still narrow, so recall caps below ~0.85
  at the probe budgets shown.
- **Red (`both`)**: the **upper-left frontier**. Reaches recall = 1.0 at
  ~143 PL fetches; reaches recall ≥ 0.95 at 72.

**At every recall target, `both` Pareto-dominates `adaptive` alone.**

### Single-cell numbers, 1 % selectivity, probe_base = 32 ([`14_4way_bars_probe32_sel1pct.png`](14_4way_bars_probe32_sel1pct.png)):

| condition | probe used | PL fetches | recall@10 |
|---|---|---|---|
| none     | 32  | 32.0  | 0.442 |
| adaptive | 256 | 256.0 | 0.970 |
| bloom    | 32  | 9.4   | 0.442 |
| **both** | **256** | **71.6** | **0.970** |

The same recall as `adaptive`, but at **3.6× fewer PL fetches**. This
is the headline production claim: bloom + adaptive gives you adaptive's
recall at bloom's I/O profile.

### What about more selective filters? ([`13_4way_pareto_sel01pct.png`](13_4way_pareto_sel01pct.png))

At 0.1 % selectivity, the gap widens dramatically:

| condition | probe used | PL fetches | recall@10 |
|---|---|---|---|
| none     | 32   | 32.0   | 0.070 |
| adaptive | 256  | 256.0  | 0.428 |
| bloom    | 32   | 0.9    | 0.070 |
| **both** | **256**  | **7.7**    | **0.428** |

`both` reaches the same recall as `adaptive` at **33× fewer PL fetches**.
At probe_base=128, `both` matches `adaptive` recall (0.874) at 30.9 PL
fetches versus 1024 — an order-of-magnitude I/O reduction.

### I/O cost to hit each recall target ([`16_4way_iso_recall_io_sel1pct.png`](16_4way_iso_recall_io_sel1pct.png))

Reading horizontally at any target recall:

| target recall@10 | none | adaptive | bloom | both |
|---|---|---|---|---|
| ≥ 0.50 | 64  | 64  | 18  | **18** |
| ≥ 0.75 | 128 | 128 | 36  | **36** |
| ≥ 0.90 | —   | 256 | —   | **72** |

| ≥ 0.99 | —   | 512 | —   | **143** |

Bars marked "—" never hit the target within the swept probe range. At
recall ≥ 0.50 / 0.75, `bloom` and `both` tie because the 8× adaptive

gate has trimmed the duds. At recall ≥ 0.90, `bloom` alone runs out of
probe budget; `both` still wins.

### Why this composition matters

The two features attack different costs:

- **Adaptive nprobe** decides *how wide to probe* in HNSW. It costs
  HNSW time (in-memory, cheap) and PL reads (expensive, scaled
  linearly). Without bloom, every probed centroid becomes a fetch.
- **Bloom gate** decides *which probed centroids to fetch*. Holds PL
  fetches near constant while drawing them from a wider candidate
  pool.

Run alone, `adaptive` solves the recall problem at high I/O cost;
`bloom` solves the I/O problem at a low recall ceiling. Together,
adaptive supplies the wide candidate pool, the gate selects the heads
worth fetching from it. The product on this workload is the recall of
`adaptive` at the I/O of `bloom`.

The codebase ships both features behind independent config flags
(`adaptive_search_nprobe`, `head_bloom_enabled`). The recommended
production deployment is to enable both.

## Re: "Surely Chroma's recall would be better than this?"

This was the right question to ask, and the short answer is: **yes, the
SPANN index itself is fine — the low absolute recall numbers in the main
report are an artefact of the bench's deliberate experimental setup, not
of SPANN's index quality.**

### What's going on

The sweep harness ([`spann_bloom_sweep.rs`](../../rust/worker/benches/spann_bloom_sweep.rs))
calls `chroma_index::spann::utils::rng_query` *directly* with a fixed
`probe_nbr` (32 by default). This is the bare HNSW-graph search — not
the production reader path.

The production code path is `SpannSegmentReaderShard::rng_query`, which
internally calls `SpannIndexReader::determine_search_nprobe`. That
function applies two boosts on top of `probe_nbr`:

1. **Size-based bucketing.** For collections under 500 K records the
   floor is 24, under 1 M it's 32, above that 64. (`adaptive_search_nprobe = true` default.)
2. **Filter-aware boost.** When the orchestrator computes the metadata
   selectivity, it scales `probe_nbr ← clip(probe_nbr / max(sel, ε),
   probe_nbr, probe_nbr · MAX_FACTOR)` with `MAX_FACTOR = 8`, `ε = 0.001`.
   This is the *adaptive nprobe* feature, already merged on `main`.

For a 1 % filter the production path would multiply `probe_nbr` by up
to 8×; for a 0.1 % filter it hits the cap at 8× as well. So a query
that the bench evaluated at `probe_nbr=32` would, in production with
adaptive nprobe, run at `probe_nbr=256`. The bench *deliberately bypasses
this* so that the bloom gate's effect is isolated from adaptive nprobe's
effect — a clean ablation.

### What happens when you let the baseline probe more

[`09_baseline_climbs.png`](09_baseline_climbs.png) is the answer to the
skepticism. It's the same SIFT1M / n=50K / 1 % selectivity workload as
the headline tables, but extends `probe_nbr` up to 512:

| probe_nbr | bloom_off recall | bloom_on_iso_io recall |
|---|---|---|
| 32  | 0.434 | 0.830 |
| 64  | 0.624 | 0.962 |
| 128 | 0.814 | 0.998 |
| 256 | 0.956 | 1.000 |
| 512 | 0.998 | 1.000 |

The baseline (bloom_off) reaches **recall = 0.998 at probe=512**, and
**recall = 0.956 at probe=256**. The SPANN index *can* achieve
near-perfect recall under the same metadata predicate — it just has to
probe a lot more centroids to do so. That matches everyone's intuition
about Chroma: the system is good, not broken.

### What the bloom gate buys you, then

[`08_iso_recall_io_cost.png`](08_iso_recall_io_cost.png) shows the
practical answer: **at every recall target, bloom_on needs about
1/3 to 1/4 the actual PL fetches of bloom_off.**

| target recall@10 | bloom_off PL fetches | bloom_on PL fetches | savings |
|---|---|---|---|
| ≥ 0.50 | 64  | 38  | 1.7× |
| ≥ 0.75 | 128 | 38  | 3.4× |
| ≥ 0.90 | 256 | 76  | 3.4× |
| ≥ 0.95 | 256 | 76  | 3.4× |
| ≥ 0.99 | 512 | 152 | 3.4× |

Interpretation: a user demanding recall ≥ 0.95 on a 1 %-selectivity
filter pays 256 blockfile reads per query without the gate, or 76 with
it. PL fetches on a production deployment are cross-host or cross-shard
network reads (or S3 in some configs); cutting them by ~3× materially
shrinks per-query latency and infrastructure cost.

### How this composes with adaptive nprobe in production

The two optimisations target different costs and stack cleanly:

- **Adaptive nprobe** decides *how wide to probe* the HNSW centroid
  graph. It raises recall by visiting more centroids when the filter is
  selective. Cost: more HNSW work (in-memory, cheap) **and** more PL
  fetches (expensive, scales linearly).
- **Bloom gate** decides *which probed centroids to actually fetch*.
  It holds PL fetches constant while drawing them from a wider pool.

The production deployment recipe is `adaptive_search_nprobe = true,
head_bloom_enabled = true, head_bloom_commit_rebuild = true`. Adaptive
nprobe sets the HNSW probe budget; the bloom gate cuts that probe set
down to the heads worth fetching. The bench's `bloom_on_iso_io`
condition is a manual stand-in for this composition: it manually
inflates `probe_nbr` to mimic what adaptive nprobe would do, then runs
the gate.

### What this study actually claims

The study isolates *the bloom gate's effect on filtered recall, holding
all other SPANN parameters constant*. Specifically:

1. **The gate never harms recall** at fixed probe count
   (iso-probe). This is a structural property; no panic was triggered
   in 6 150 query × condition measurements.
2. **The gate cuts I/O at fixed recall** by 3–4× on selective
   predicates (from sweep A and the iso-recall analysis here).
3. **The gate does nothing on unselective predicates** (≥ 5 %
   selectivity); cost is one bloom check per probed head.

These claims are independent of whether adaptive nprobe is on, of
production-tuned `ef_search`/`search_nprobe` defaults, of storage
backend, and of dataset. They live in the bloom layer alone.

The absolute recall numbers in the main report are *not* a recall claim
about Chroma's SPANN — they are the dependent variable in an
isolation-of-effects ablation. To read absolute recall as "Chroma's
production recall" you would have to add back: adaptive nprobe (×4–×8
on probe budget at 1 % selectivity), production-tuned `ef_search`, real
metadata distribution rather than uniform synthetic buckets, and the
production HNSW M / efConstruction settings. Those are the right
numbers to report in a Chroma performance benchmark; they are not the
right numbers to report in an *ablation study of the bloom gate*. The
two reports answer different questions.

### Reading the plots

[`04_selectivity_grid.png`](04_selectivity_grid.png) is the most
information-dense plot. The left panel shows that the baseline's
recall problem is sharpest at low selectivity — the 0.01 % curve is
visually flat near zero across the whole probe sweep. The right panel
shows the gate (with iso-I/O) collapses the four curves toward each
other and toward 1.0; selectivity stops being the dominant factor.

[`05_drop_ratio_vs_selectivity.png`](05_drop_ratio_vs_selectivity.png)
makes the design space explicit: drop_ratio rises monotonically as
selectivity falls. At 10 % selectivity the gate is essentially idle
(drop_ratio = 0.058); at 0.01 % it's saturated (drop_ratio = 0.997).
The "is this gate worth turning on?" decision is a function of the
expected query mix, not of the index.

[`07_maintenance_modes.png`](07_maintenance_modes.png) is the most
important *implementation* plot. Phase 1 MVP and Option 1 alone both
have drop_ratio = 0 — i.e. they implement the bloom feature correctly
but the gate fires on nothing. Only Option 2 (commit-time rebuild) is
effective. This is non-obvious from the spec's high-level descriptions
and was the most interesting bug surfaced by the implementation work.

## Reproducing the plots

```bash
# from repo root, with the .venv created during this run:
source .venv/bin/activate
python LOGS_ACTIONS/2026-05-02-plots/make_plots.py
```

The script reads CSVs from
`LOGS_PLANS/benchmarks/recall_study/` and writes PNGs alongside itself.
If a CSV is missing it will warn and skip the corresponding plot;
delete a PNG and re-run to regenerate just that one.

If you want to regenerate the underlying CSVs themselves, see
§4.5 of [`bloom-filters-recall-study.md`](../../LOGS_PLANS/bloom-filters-recall-study.md)
for the bench commands. Each sweep takes about 1–2 minutes per cell on
an M-series MacBook with a release-mode bench binary.
